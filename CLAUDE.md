# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Creatorske — a marketplace connecting Kenyan content creators with brands. React 18 + Vite SPA (JavaScript, not TypeScript — `jsconfig.json` provides path aliasing/editor support only, there is no type checking). This repo is the frontend only; it talks to a separate backend API over REST (axios).

**Every page is wired to the API; there is no mock data left in `src/`.** The full contract (every path, request body and response shape the pages read) is `BACKEND_API_SPEC.md`, and it is implemented end-to-end by the **local mock backend in `backend/`** (Express + seeded data, `cd backend && npm install && npm start` on :5000; sign-ins and layout in `backend/README.md`). `backend/` is git-ignored and must never be committed or pushed - it exists so the frontend can be developed and demoed as a working product until the real API lands. When you add a frontend feature, add its endpoint to the mock and to the spec in the same change; when a page needs a field, seed it rather than hardcoding it in the page. Before implementing a new component, check a sibling feature (e.g. `features/auth`, `features/rate-card`) for the established pattern rather than inventing a new one.

## Commands

```bash
npm run dev       # start Vite dev server
npm run build     # production build
npm run preview   # preview a production build locally
npm run lint      # eslint . --ext js,jsx --report-unused-disable-directives --max-warnings 0
```

There is no test runner configured in this repo yet.

`.claude/launch.json` configures `npm run dev` (port 5173) for Claude Code's browser-preview tool — it's dev tooling for driving the app in-browser during a session, not part of the app itself.

**`npm run lint` is currently broken as written.** Both an old-style `.eslintrc.cjs` and a flat `eslint.config.js` exist; ESLint 8.57 (the installed version) auto-detects `eslint.config.js` and switches to flat-config mode purely because the file exists — but that file uses `eslint/config`, a subpath that doesn't exist until ESLint 9, so linting crashes with `ERR_PACKAGE_PATH_NOT_EXPORTED` before it reaches `.eslintrc.cjs` at all (the `package.json` script's `--ext` flag then also fails separately, since flat-config mode doesn't support it). To actually lint with the existing `.eslintrc.cjs` rules, force legacy mode: `ESLINT_USE_FLAT_CONFIG=false npx eslint . --ext js,jsx --report-unused-disable-directives --max-warnings 0` (PowerShell: `$env:ESLINT_USE_FLAT_CONFIG='false'; npx eslint . --ext js,jsx --report-unused-disable-directives --max-warnings 0`). Doing so currently surfaces ~66 pre-existing errors (mostly `react/no-unescaped-entities` apostrophes in JSX text and a few genuinely unused imports/vars) scattered across pages — none of that is related to the API-wiring work above.

## Architecture

**Feature-based structure under `src/features/<feature>/`.** Each feature follows the same internal layout (not every feature has every folder — only what it needs):
- `components/` — feature-specific UI (`.jsx`)
- `hooks/` — TanStack Query hooks wrapping the service layer (`.js`)
- `services/` — one object per feature exporting API methods that call `src/lib/api.js` (e.g. `authService.login(...)`, naming is `camelCaseService`)
- `constants/` — enums/lookup objects (e.g. status strings)
- `utils/` — feature-local helpers
- `index.js` — the feature's public export surface; import from here from outside the feature rather than reaching into its internals

Features: `auth`, `onboarding`, `rate-card`, `portfolio`, `enquiry`, `messaging`, `payments`, `reviews`, `notifications`, `plans`, `creator-dashboard`, `brand-dashboard`, `admin`, `directory`.

Service/file naming is not perfectly consistent across features (e.g. `payments/services/payment.service.js` is singular while the feature folder is plural) — match the existing file's name in that feature rather than assuming a rule.

**Pages vs. features.** `src/pages/<role>/*Page.jsx` are route-level containers grouped by audience (`public/`, `auth/`, `onboarding/`, `creator/`, `brand/`, `admin/`) that compose components from one or more `features/`. Routing lives entirely in `src/routes/index.jsx` as one `createBrowserRouter` tree; each role segment is wrapped in `<ProtectedRoute requiredRole="...">` and a role-specific layout from `src/components/layouts/`.

**`ProtectedRoute` (`src/routes/ProtectedRoute.jsx`) enforces auth + role** — redirects to `/login` if unauthenticated, or to the user's own role home (`ROLE_HOME`) if they're logged in but hit the wrong role's routes. Because it reads `useAuth()` reactively, calling `logout()` anywhere causes an immediate redirect with no extra `navigate()` call needed in the caller.

**Auth state** lives in `src/context/AuthContext.jsx` (a plain React context, not a feature service) — token/user in `localStorage` under `creatorske_token` / `creatorske_user`, exposing `user`, `role`, `isAuthenticated`, `login`, `logout`, `updateUser`. `logout()` also fires a best-effort `POST /auth/logout` before clearing local state. `features/auth/hooks/useAuth.js` just re-exports `useAuth` from this context. `auth.service.js` also exports a `userService` (profile/password endpoints) alongside `authService` — there's no separate "users" feature folder, so `/users/*` lives there since it's the closest fit. `NotificationContext` (`src/context/NotificationContext.jsx`) follows the same context pattern and independently polls `notificationService.getUnreadCount()` every 30s for the navbar bell — this is separate from `features/notifications/hooks/useNotifications.js`, which is the full list/mark-read hook for `NotificationList.jsx`.

**API layer**: `src/lib/api.js` is a single shared axios instance (`apiClient`, default export) plus a few standalone named exports for endpoints with no natural feature home — `uploadFile`/`getUpload`/`deleteUpload` and `getHealth`. Request interceptor attaches the bearer token from `localStorage`; response interceptor normalizes errors to `{ status, message, data }` and force-redirects to `/login` on 401. Every feature service imports this instance rather than creating its own axios client. Base URL comes from `VITE_API_BASE_URL` — `.env.development` points at the local mock backend (`http://localhost:5000/api`) and `.env.production` at the real API's tunnel; the token is also appended as `?token=` on links that open in a new tab (invoice PDFs).

**Data fetching**: TanStack React Query, one `QueryClient` created in `src/main.jsx` (`staleTime: 60s`, `retry: 1`, `refetchOnWindowFocus: false`). Feature hooks (`useEnquiries`, `usePayments`, etc.) are expected to wrap `useQuery`/`useMutation` around the matching service — mutation errors are handled per-feature via `sonner` toasts, there's no global mutation error handler.

**Styling**: Tailwind + a hand-tuned CSS custom-property design system defined in `src/index.css` (`:root` for light mode, `.dark` class for dark mode) — this is the source of truth for colors, spacing, type scale, radii, and shadows; `tailwind.config.js` mostly just extends Tailwind to reference these tokens rather than hardcoding its own values. Use `cn()` from `src/lib/utils.js` (clsx + tailwind-merge) whenever composing conditional class names — this is the shadcn/ui convention and is used project-wide. `src/index.css` also ports a component-library class set (`.btn-*`, `.card`, `.stat-card`, `.tag-*`, `.data-table`, `.sidebar-link`, etc.) 1:1 from an external "Creatorske Component Library" doc — when a component needs one of these visual patterns, reuse the existing class names rather than rebuilding the styles with raw Tailwind utilities.

**Typography**: there is one heading system and it lives in `src/index.css` as semantic role classes mapped onto the `--text-h*` scale: `.display-title` (36-56px fluid, weight 700, the single marketing headline on the home hero), `.hero-title` (28px, auth/onboarding headers and marketing section headings), `.page-title` (22px, the single heading at the top of a dashboard page), `.card-title` (18px, large card), `.section-title` (16px, section or small card heading, table header), `.eyebrow` (10px uppercase purple), `.field-label` (11px uppercase form label, `+ .field-required` for the asterisk), `.lead` (16px body-lg intro paragraph under a display/hero title), `.page-subtitle` (13px grey line under a title), `.text-hint` (12px grey helper text). Marketing pages use the same roles - display-title / hero-title / card-title / section-title / eyebrow / lead - with colour overrides on dark surfaces, never their own clamp() sizes. Use the role, never a raw `fontSize`/`fontFamily: var(--font-display)` on a heading, and never define a page-local heading class - both of those are how the app ended up with 19 different heading styles before this existed. Section titles are text only (no leading icon). Heading weight is 600 everywhere except the marketing `h1` (700). Numeric stat displays (`.stat-card-value` and friends) are the one legitimate exception to the scale.

**Spacing**: one 4px grid, tokens only. Every padding, margin and gap in the app - inline `style`, page-scoped `<style>` blocks, `index.css` - is a `var(--space-N)` step from `2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80, 96` (`--space-2` is for hairline icon nudges only). Never write a raw pixel value for spacing, never add an off-grid token (there used to be 5/6/7/9/10/28/38 - they were the reason nothing lined up), and in Tailwind-built pages use whole-step utilities (`gap-2`, `p-4`), not `gap-1.5`/`px-2.5`/`p-[18px]`. Reach for the semantic tokens before a bare step: cards have exactly three padding tiers, `.card-p-sm` 16 (compact rows/tiles), `.card-p-md` 24 (the default; `.stat-card` also uses it), `.card-p-lg` 32 (roomy hero/summary/settings sections) - there is no `.card-p-xl`; page edges are `--gutter-dashboard` (32, the three dashboard `__main` panes), `--gutter-public` (48, marketing/auth/onboarding navbars, bands and content containers - in Tailwind pages as `px-[var(--gutter-public)]`), and both collapse to `--gutter-mobile` (16) under 640px through a single `@media` rule on `:root` in `index.css`, so pages must not add their own mobile padding overrides; `--input-icon-pad` (40) is the text inset for an input with a leading/trailing icon. When a design calls for a value between steps, snap to the nearer step (ties round up).

**Iconography**: one source, `@tabler/icons-react`, imported per file (`import { IconPlus } from '@tabler/icons-react'`). The Tabler *webfont* (`<i className="ti ti-*">`, loaded from a jsDelivr `@latest` URL at runtime) is gone - it was injected from ten different files and rendered as boxes whenever the CDN CSS didn't apply - so never add it back, never hand-draw an inline `<svg>` for a glyph Tabler already has, and never use a text character (`×`, `→`, `★`) as an icon. Size and stroke are set by CSS, not props: `svg.tabler-icon` in `index.css` fixes `stroke-width: 2` and a default size, and every icon carries exactly one size class from `.icon-xs` 12 (beside caption/hint text), `.icon-sm` 14 (the default: buttons, tags, inputs, inline with body text), `.icon-md` 16 (navbar, sidebar, icon-only buttons, tab pills, callouts), `.icon-lg` 20 (section/card leads, hamburger, provider tiles), `.icon-xl` 24 (empty states and success/error result screens) - the `size`/`stroke`/`strokeWidth` props are never passed, because the CSS overrides them anyway. Colour is always inherited (`currentColor`); set it on the parent or with a `style={{ color }}`, and mark decorative icons `aria-hidden="true"`. Components that take an icon as data hold the component reference, not a string (`{ icon: IconWallet }` rendered as `<item.icon className="icon-md" />`), and `EmptyState`/`ErrorState` size their own icon, so callers pass it bare (`icon={<IconInbox />}`).

**Charts**: one library, Recharts, wrapped once in `src/components/charts/` - `TrendChart` (area for one series, lines for 2-4, `emphasis` to spotlight one), `BarChart` (columns; `layout="horizontal"` for long category names with `labels` at the tip; `stacked` for part-to-whole), `DonutChart` (part-to-whole for <= 4 categories, headline figure in the hole, its list doubles as legend and direct labels), `Sparkline` (stat-tile trend, no axes), `Meter` (one ratio against a limit - never a two-slice pie), all inside `ChartFrame` (title, subtitle, legend, period pills via `ChartPeriod`, and the loading/error/empty states). Never import `recharts` directly in a page, never hand-roll a bar chart out of divs, never a dual-axis chart, never more than four series. Styling lives in `chartTheme.js` + the `.chart-*`/`.donut*`/`.meter*` rules in `index.css`: series colours are the fixed-order `--chart-1..4` tokens (validated for CVD in light and dark; slots 3-4 are under 3:1 on white, so every multi-series chart carries a legend and tooltip), marks are thin (bars <= 24px with a 4px rounded data end, 2px lines, 10% area wash, 2px surface gap between stacked segments), gridlines are hairline `--chart-grid`, and text in charts always wears text tokens, never a series colour. Format values with `kes`/`compact`/`pct` from the kit.

**No demo data**: every figure on screen comes from a query. A failed query renders `ErrorState` (with retry where it makes sense), a successful-but-empty response renders `EmptyState`, and loading renders `Skeleton` - never a fabricated number and never a page-local sample. Mutations toast the server's `err.message`. Account-level data has shared hooks: `features/auth/hooks/useProfile.js` (`useProfile()` for `/users/profile` + save, `usePreferences()` for `/users/preferences`), `features/payments/hooks/usePayoutMethods.js` (creator payout methods), `features/brand-dashboard/hooks/useBrandAccount.js` (`useBrandPaymentMethods`, `useBrandTeam`); settings tabs load through these and keep a local `draft` only for unsaved edits. The rate-card builder seeds a new card from `useProfile()` and stores `platforms` as an on/off map (`{ instagram: true, ... }`); the mock returns that same shape. The sidebar has no disabled placeholder items - if a page isn't built, it isn't listed.

**Settings pages**: all three roles share one shell and one category order - `Profile · Account · Notifications · <money> · [Team] · Appearance · Privacy & data` - from `src/components/settings/` (`SettingsShell` with `?tab=` in the URL, `SaveBar`, `Toggle`/`ToggleRow`, `Field`, `DangerZone`) plus shared cards (`LoginDetailsCard`, `TwoFactorCard`, `SessionsCard`, `LanguageRegionCard`, `ThemeCard`, `AccentCard`, `DisplayCard`, `DataExportCard`, `LegalCard`, `TeamCard`). "Account" always holds sign-in, password, 2FA, sessions, language and the danger zone; the money slot is Payouts (creator), Billing (brand) or Platform (admin, the marketplace rules); Team appears for brands and admins; admins have no Privacy tab and 2FA is required. The settings CSS lives once in `index.css` (`.settings-*`, `.toggle-row`, `.danger-zone`, `.session-row`, ...) - never redefine it in a page. Add a role-specific section as a card inside the right tab, never as a new tab.

**Navbar search**: the three dashboard layouts share `components/layouts/NavbarSearch` - inline field on desktop, an icon button under 600px that opens a full-width sheet beneath the navbar (autofocus, Escape/X closes). Layouts only pass `placeholder`, `ariaLabel` and `onSubmit(query)`. `CollapsibleCard` takes a `description` shown only while folded, so a collapsed settings card still says what is inside - give every collapsible card one.

**Motion**: nothing appears abruptly. `components/layouts/PageTransition` wraps every layout's `<Outlet>` and re-runs `.page-enter` on each pathname change (not on query changes); modals scale in (`.ui-modal`), dropdown/menu popovers and the notification panel drop in (`.menu-appear`), folded cards unfold, chart bodies fade in. All of it is 120-240ms ease-out and disabled by `prefers-reduced-motion` or the `reduce-motion` class the Display card sets (restored on boot by `ThemeContext`). Add new appearing UI to that list in `index.css` rather than inventing a new animation.

**Navbar avatar**: `components/layouts/NavAvatar` - profile photo when the user has one, otherwise initials from name / company / email (never "?"); it links to `/<role>/settings?tab=profile`. Dashboard pages never paint their own background - the content pane owns `--page-bg`, so a page-level background shows as a lighter box in dark mode.

**Dropdowns**: every "pick one" control is `components/ui/Select` (`value`, `onChange(value)`, `options: [{ value, label, hint?, icon?, disabled? }]`, `placeholder`, `size`, `variant="pill"` for filter rows, `className` for a page's own input class). It draws its own listbox in a portal (same look in every browser and in dark mode, flips upward when there is no room, full keyboard support), so **native `<select>` is not used anywhere** - with react-hook-form wrap it in `<Controller>`. Action menus ("do one") use the same popover rules: `.menu-popover` / `.menu-item` / `.menu-item--danger` / `.menu-divider`. Focus rings are global: none for mouse users, a 2px brand ring on `:focus-visible` for keyboard users.

**Path alias**: `@/` maps to `src/` (configured in both `vite.config.js` and `jsconfig.json`) — always import via `@/...` rather than relative `../../..` paths.

**Role model**: three roles — `creator`, `brand`, `admin` — each with its own dashboard, layout, and route namespace (`/creator/*`, `/brand/*`, `/admin/*`). Each dashboard layout (`CreatorLayout`, `BrandLayout`, `AdminLayout`) pulls its navbar avatar/initials from `useAuth()`, its logout button from `useAuth().logout`, its notification-bell badge from `NotificationContext`'s `useNotifications()`, and its sidebar badge counts from the relevant feature hook (`useEnquiries().pipelineCounts`, `useBrandDashboard().activeCampaignCount`, `useDisputes()`/`useFlaggedAccounts()`/`useAdmin()`) — all counts degrade to no badge rather than crashing when a query is loading or errors. `PublicLayout`, `AuthLayout`, and `OnboardingLayout` are still bare placeholder shells (`// TODO: build this layout in Phase 4`) with no chrome beyond `<Outlet/>`; several pages that render inside them (`LoginPage`, `SignUpPage`, `HomePage`) build their own full-page layout inline instead of relying on the shell. `src/features/plans/utils/planGate.js` checks `user.plan.features.includes(feature)`; the separate `ProtectedFeature`/`UpgradePrompt` components in `components/shared/` use their own independent plan-rank comparison (`user.plan` string vs. `starter/pro/business`) rather than calling `planGate` — the two aren't wired together.

**Currency/locale formatting**: use the helpers in `src/lib/utils.js` (`formatCurrency` → `KES` via `en-KE`, `formatDate`, `formatRelativeDate`, `formatCount`, `getInitials`) instead of formatting dates/numbers inline — the app is Kenya-specific (KES currency, `en-KE` locale).

**Responsive conventions**: the app has three uncoordinated breakpoint systems that were never unified (deliberately left that way — retrofitting one convention across a dozen already-correct files was judged higher regression risk than benefit): the three dashboard layouts hide their sidebar and switch to a mobile hamburger+drawer at **860px** (with a secondary 600px tweak for padding/search), most public marketing pages (`Home`/`Directory`) use **900px** for their own ad hoc `@media` rules, and pages built with Tailwind utility classes (`RateCardPage`, `PortfolioPage`, `PricingPage`) use Tailwind's default `sm`/`md`/`lg` scale (640/768/1024px). When fixing a responsive gap, match whichever convention that specific file (or its closest sibling) already uses rather than introducing a fourth number. `CreatorLayout`/`BrandLayout`/`AdminLayout` each independently duplicate the same hamburger-menu-button + slide-in-drawer pattern (a `<button className="btn btn-square btn-icon-style dashboard-shell__menu-btn">` toggling a `drawerOpen` state, a `.sidebar.mobile-open` CSS override scoped inside each layout's existing 860px query, and a backdrop `<div>`) — same duplication-per-layout convention these files already followed before this existed, not a shared `DashboardShell` component.

**Enquiry + chat flow**: an enquiry *is* its chat thread, for its whole lifecycle (new → in review → booked → completed) — `MessageThread`'s `threadId` prop is always the enquiry's own id, never a separate campaign/thread id, because the API doc has no dedicated thread-creation endpoint (this convention was already implied by a pre-existing code comment in `useMessages.js` before this feature was built out). `src/features/enquiry/` and `src/features/messaging/` are both real now: `EnquiryForm`/`EnquiryCard`/`EnquiryDetail`/`EnquiryPipeline` and `MessageThread` are actual components (not stubs), wired through `useEnquiries()`/`useCreateEnquiry()`/`useMessages(threadId)`. `ActivityLog.jsx` and `ScopeConfirmation.jsx` remain intentionally unbuilt — no documented endpoint backs a real activity timeline or a scope-confirmation step. Chat threads never auto-close (a deliberate product decision, not a gap). `components/ui/Modal.jsx` is a real, generic, portal-based modal (`open`/`onClose`/`title`/`size`/`children`) — use it rather than building another one-off modal.

The public rate card (`/c/:handle`) is where a brand starts an enquiry, but `POST /enquiries` requires an authenticated brand. Anonymous "Send enquiry" clicks are redirected through `/login?redirect=<path>`, with `sessionStorage[POST_AUTH_REDIRECT_KEY]` (`src/features/auth/constants/roles.js`) as the durable fallback carrier — a query param alone doesn't survive a signup → verify-email → login hop that can happen in a different tab. `LoginPage.jsx` reads both and clears the sessionStorage key after use. Brands manage their sent enquiries at `/brand/enquiries` (mirrors the creator's `/creator/enquiries`, minus accept/decline — only the receiving creator can act on an enquiry).

`POST /enquiries` takes `{ creatorId, packageId, message }` and `GET /brands/campaigns/:id` carries `enquiryId` (the chat thread) plus `messages`, `deliverables`, `deliveredFiles`, `activity` and `review`; `CampaignDetailPage.jsx` renders that response only, with approve/dispute/review mutations invalidating it.

**Marketing home** (`pages/public/HomePage.jsx`): the structure is the Creatorske waitlist page's - a creator/brand role switch (`?for=brand`, remembered in localStorage) that rewrites every section's copy from the `COPY` table, a centred black hero with purple streaks, three illustrated steps (`public/images/marketing/*.webp`, from the waitlist's illustrations, resized to 960px), a features row, an FAQ accordion and a gradient closing banner, with `.hp-reveal` scroll-reveal. `/signup?role=brand|creator` skips the sign-up role step. Step cards are chrome-less (no border/shadow) by request.

**Public page convention**: `HomePage`, `DirectoryPage`, `RateCardPage`, and `PricingPage` (all under `pages/public/`) follow a different styling convention than the dashboard pages — Tailwind utility classes plugged with the global `index.css` CSS-variable tokens (e.g. `text-[var(--black)]`, `bg-[var(--purple-50)]`), plus a small page-scoped `<style>` block for a handful of custom nav/button classes (`.hp-*` on Home, `.dir-*` on Directory, `.pr-*` on Pricing) — each page defines its own copy rather than sharing one sheet. This is deliberately different from the shared `.card`/`.btn-*`/`.tag-*` class set the dashboard layouts and pages use; match whichever convention the page you're editing already uses rather than mixing them. `PricingPage.jsx`'s tier content (`src/features/plans/constants/pricingTiers.js`, `BRAND_PRICING_TIERS`/`CREATOR_PRICING_TIERS`) is presentation copy transcribed from a product pricing sheet — separate from `plans.js`'s `PLANS` enum, which tracks a user's actual account plan state.

**Rate-card completeness** is computed client-side in `useCreatorDashboard()` from `listRateCards()` (package count and payout methods against the plan limits); `GET /rate-cards/health` is only a module health check and is never read as a score.
